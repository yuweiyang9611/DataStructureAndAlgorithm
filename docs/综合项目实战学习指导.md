# 数据结构与算法综合项目实战学习指导

## 1. 为什么需要综合项目

单独实现堆、哈希表、图或动态规划，训练的是局部不变量；真实需求却通常是“让更多订单按时送达”“让搜索结果更相关”“在资源有限时缩短工期”或“让数据在进程重启后仍可恢复”。综合项目要完成的关键转换是：

1. 把业务语言翻译为顶点、边、键、区间、状态、约束和目标函数。
2. 先写清楚优化目标的优先级，再选择算法，避免“算法能跑，但优化的是另一件事”。
3. 让每种数据结构只承担它擅长的职责，不把所有状态都塞进一个字典。
4. 把算法结果恢复为路线、搜索命中、任务时间表或存储记录。
5. 明确模型没有表达什么，并用不变量、模型测试、性质测试和差分测试持续提供证据。

本阶段提供四个可运行的 `.NET 10` / `C# 14` 控制台项目：

| 项目 | 应用场景 | 主要数据结构 | 主要算法 |
| --- | --- | --- | --- |
| CityDelivery V2 | 城市即时配送与车辆分单 | 开放寻址哈希表、带权图、并查集、LRU、二叉堆 | A*、最小费用最大流（生产路径）、穷举匹配 oracle（测试对照）、Prim |
| MiniSearch V2 | 小型文档搜索、补全与纠错 | 位置倒排表、Trie、BK-tree、LRU、二叉堆 | BM25、短语/邻近检索、Aho-Corasick、编辑距离 |
| ProjectScheduling V2 | 有依赖和资源上限的项目排期 | DAG、二叉堆、懒标记线段树 | Kahn、关键路径 DP、贪心列表调度、小规模精确搜索 |
| MiniStorage | 可恢复的教学型键值存储 | B+ 树、Bloom Filter、LFU、WAL | 点查、范围扫描、预写日志、崩溃恢复、墓碑删除 |

“尽量自己实现”不等于拒绝 BCL。核心索引、缓存、图算法、区间结构和恢复流程优先使用仓库中的教学实现；JSON 序列化、字符串构建和只读结果集合继续使用标准库。判断标准是：如果替换这个组件会改变本项目要学习的不变量或复杂度，它就值得手写；如果它只是外围基础设施，应优先使用成熟库。

## 2. 四个项目共用的分层原则

每个项目都保留三层职责：

- 领域记录表达输入和输出，不在属性访问器里偷偷执行算法。
- 规划器或引擎把领域约束翻译成算法输入，并把内部结果恢复为领域结果。
- `Program.cs` 只构造可重复样例，并选择普通 JSON、追踪 JSON 或 Mermaid 输出。

这样写不是为了形式上的“分层”，而是为了建立可验证的依赖方向：算法层不知道控制台和序列化格式；测试可以直接调用引擎；同一套核心逻辑也可以接到 Web、桌面或文件输入。代码中仍允许 `List<T>` 和数组承担连续缓冲区职责，不应为了“全手写”而制造没有教学价值的包装。

另一个共通原则是先定义契约：空输入怎样处理、重复键是否覆盖、区间是左闭右开还是双闭、相同得分如何稳定排序、缓存键包含哪些版本状态。综合项目中的许多错误并不来自算法公式，而来自两个模块对同一契约理解不同。

## 3. 项目一：城市即时配送 V2

### 3.1 应用场景与两层目标

配送站接收订单和空闲车辆。车辆必须满足载重、方向可达和截止时间约束，每辆车在一轮中最多领取一个订单。V2 把目标明确为字典序优化：

1. 首先最大化成功分配数量；
2. 在最大分配数量相同的方案中，最小化总旅行时间。

为什么必须分两层写？如果只最小化费用，算法可能选择“不派任何车”，费用为零但没有业务价值；如果只做最大匹配，同样能配送三单的两个方案中可能选到绕远方案。目标函数必须先于算法选择。

### 3.2 为什么路线图和维护图分开

旅行时间图是有向图，因为单行道只允许一个方向；维护网络回答设施之间是否要保留连接，通常按无向图处理。项目因此从同一批道路构造两个视图：

- `WeightedGraph<string>(isDirected: true)` 保存旅行分钟数；
- `WeightedGraph<string>(isDirected: false)` 保存维护成本。

把二者混成一张图，会把“能否按方向行驶”和“物理设施是否连接”混为一谈。Prim 运行在无向维护图上，A* 运行在有向旅行图上，这是领域语义决定的数据结构边界。

### 3.3 为什么先并查集预筛，再运行 A*

并查集近似常数时间判断两地是否处于同一弱连通分量。若不连通，候选必然不可达；若弱连通，仍不代表存在有向路径，所以还要运行 A*。这是“便宜的必要条件 + 较贵的充分验证”：

1. 容量不足、弱连通失败时立即拒绝；
2. 其余候选用 A* 验证方向和最短旅行时间；
3. 再检查截止时间，得到可行的车辆—订单边。

输入没有能证明可采纳性的地理启发函数，因此项目使用 `h(n) = 0`。A* 此时退化为 Dijkstra，但仍保持最优性。宁可选择可证明正确的退化形式，也不应使用可能高估剩余成本的“看起来更聪明”的启发函数。

### 3.4 从最大匹配升级到最小费用最大流

Hopcroft-Karp 只回答“最多能匹配多少对”，不优化匹配边的费用。V2 的生产路径直接构造下面的流网络；
测试再用小规模穷举最大匹配作为独立参照，避免“流算法自己证明自己”：

```text
源点 -> 每辆车 -> 每个订单 -> 汇点
```

- 源点到车辆、订单到汇点的容量均为 1，保证一车一单。
- 车辆到订单只为可行候选建边，容量为 1，费用为最短旅行分钟数。
- 每轮用 Johnson 势能把残量边的约化费用保持为非负，再用项目自实现二叉堆运行 Dijkstra。
- 一直增广到残量网络不存在源汇路径；此时流量自然达到最大值。配送网络的源边容量为 1，
  所以每轮最多增加一个分配，而通用实现仍允许一次发送整条路径的瓶颈流量。

这样写把“流量”和“费用”分开：流量证明第一目标，费用优化第二目标。测试也应分别断言分配数等于最大匹配、总旅行分钟数等于小规模穷举 oracle，而不能只看某一组具体匹配编号。

残量网络中的反向边费用取相反数，它允许后续增广撤销早先的局部选择。若没有反向边，算法会退化为不可回退的贪心选择，不能保证全局最小费用。

### 3.5 缓存、确定性与复杂度

路线缓存键包含 `(MapVersion, From, To)`。道路变化后即使起终点相同，旧路线也不再属于同一查询。输出总是显式排序，不依赖哈希表枚举顺序；费用相同时使用稳定的车辆和订单编号打破平局，使测试、追踪和不同平台输出可复现。

设地点数为 `V`、开放道路数为 `E`、车辆数为 `C`、订单数为 `O`、可行边数为 `M`、最终分配数为 `F`：

- 单次零启发 A*：`O((V + E) log V)`；
- 最坏候选构造：`O(CO(V + E) log V)`；
- 小规模测试 oracle 可用 Hopcroft-Karp 或完整枚举核对最大基数；它不在 V2 派单生产路径上；
- 带势函数的逐次最短增广路约为 `O(F · (C + O + M) log(C + O))`；
- Prim 最小生成森林：`O((V + E) log V)`。

限制也要明确：教学版没有地理空间索引、批量最短路、动态交通权重和并发订单锁；最小费用流虽然实现了 Johnson 势能，
但使用 `double` 成本，也没有负原始费用初始化、cost-scaling 或大规模内存调优。
约化成本的理论值应非负，但大势能加减会吞掉低位；实现按操作数尺度计算 8 ULP 误差预算，只把预算内的小负数钳为零，Dijkstra 松弛仍严格比较每个可表示成本，避免 epsilon 把真实便宜路径当平局。

## 4. 项目二：迷你搜索引擎 V2

### 4.1 为什么第一版词频索引不够

第一版倒排表记录“词出现在哪些文档、出现多少次”，足以完成 AND 查询和简单词频排序，却回答不了：

- 两个词是否连续出现；
- 两个词相距是否不超过指定窗口；
- 常见词和稀有词是否应有相同权重；
- 大词典纠错是否必须扫描每个词。

V2 因此把 posting 扩展为“文档编号 + 词频 + 有序位置列表”。位置索引多占用空间，却把短语和邻近检索从重新扫描全文变成 posting 内的位置检查。这是典型的以索引空间换查询时间。

### 4.2 位置列表为什么保持有序

分词时按文本顺序追加位置，天然得到递增列表。查询短语 `data structure` 时，要寻找
`position(structure) = position(data) + 1`；邻近查询则检查位置差是否落在允许窗口内。

当前教学代码为了让位置判定最直观，使用顺序查找和位置对枚举，只检查 posting 而不重新扫描正文；
下一步可在不改变公开语义的前提下升级为双指针，把两个位置表的合并降为线性时间。
有序仍是这个优化的前提。若位置单位在“字符偏移”和“词元序号”之间混用，短语语义也会错误；
代码选择词元序号，是因为它不受单词字符长度影响，且邻近窗口更容易解释。

### 4.3 为什么使用 BM25，而不是直接累加词频

直接累加词频会偏爱长文档，也会让到处出现的常见词占据过高权重。BM25 同时考虑：

- `TF`：词在当前文档中的出现次数，但收益逐渐饱和；
- `IDF`：词越稀有，区分能力越强；
- 文档长度归一化：减少长文档仅因词多而获益的偏差。

教学实现把公式拆成命名清晰的中间量，而不是压成一行。这样测试可以分别验证文档频率、平均文档长度和最终排序。词频饱和项把分子、分母同时按 `max(1, k1)` 缩放，使 `k1 = double.MaxValue` 时仍得到有限的等价结果。
浮点公式测试使用容差，公开排序则严格比较实际 `double`；只有分数完全相等才按文档编号决胜，避免 epsilon 比较器破坏传递性。

BM25 仍不是“相关性真理”：它不了解同义词、语义和用户意图。项目的目的，是展示目标函数如何从朴素频次升级为可解释的统计权重。

### 4.4 短语、邻近和高亮分别解决什么

- 短语检索要求词序和相邻关系完全匹配。
- 邻近检索允许两个词之间有有限间隔，适合表达“概念彼此靠近”。
- Aho-Corasick 在最终少量文档中一次扫描恢复多个查询词的字符命中位置，用于展示高亮。

位置倒排表负责缩小候选和判定词元关系，Aho-Corasick 负责最终文本展示。二者看似都处理“位置”，实际处于不同流水线阶段，不应合并为一个职责模糊的结构。
分词与整词高亮共享同一套 `Rune` 规则；高亮虽然返回 UTF-16 下标，判断左右边界时仍解码完整 Unicode 标量，不能把辅助平面字母的高、低代理项误当分隔符。

### 4.5 为什么纠错升级为 BK-tree

朴素纠错对词典中每个词计算 Levenshtein 距离，规模增大后成本明显。BK-tree 利用编辑距离满足三角不等式：若当前节点与查询词距离为 `d`，允许误差为 `r`，只需访问边标签位于 `[d-r, d+r]` 的子树。

代码仍保留编辑距离作为度量，BK-tree 只负责剪枝搜索空间。插入时，以“新词到当前词的距离”选择子边；相同距离继续下沉。这个结构的性能依赖词典分布，最坏仍可能接近线性扫描，因此文档和基准不把它宣传为无条件 `O(log n)`。

### 4.6 Top-K、缓存与复杂度

兼容的 V1 AND 查询在候选很多而只需要前 `K` 个时维护容量为 `K` 的最小堆，复杂度为 `O(N log K)`。
V2 BM25 为了让实现保持简单、确定且便于和独立公式逐项核对，当前先计算并稳定归并排序全部候选，再截取前 `maxResults` 个结果，复杂度为 `O(N log N)`；它严格按实际返回的 `double` 分数降序，只有分数完全相等时才以文档编号决胜。
独立公式测试用容差核对数值，但排序比较器本身不能使用会破坏传递性的 epsilon。生产级 Top-K 可以改用容量为 `K` 的堆，把排序阶段降为 `O(N log K)`。

V1 兼容查询的缓存键包含索引版本、规范化查询和结果数，新增文档后版本变化，旧缓存自然失效。
V2 的 BM25、短语和邻近入口目前不缓存，避免在教学第一版里遗漏 `k1`、`b`、模式或距离参数而错误复用结果；
若以后增加高级查询缓存，所有这些参数都必须成为缓存身份的一部分。

设总分词量为 `T`、posting 访问量为 `P`、候选数为 `N`、最终结果数为 `K`：

- 建立位置索引平均 `O(T)`；
- AND/BM25 候选累计约 `O(P)`；
- 当前短语/邻近位置判定最坏为位置数乘积；双指针版本可降为两个位置表长度之和；
- V1 Top-K 为 `O(N log K)`，V2 BM25 完整排序为 `O(N log N)`；
- BK-tree 平均访问节点数取决于词典分布，最坏 `O(vocabularySize · editDistanceCost)`。

教学版限制包括：按 `Rune` 识别字母数字但没有语言相关分词、Unicode normalization、增量合并和删除段；BM25 提供可配置 `k1`/`b`，但没有训练或语言相关调参。

## 5. 项目三：项目调度 V2

### 5.1 两个问题：得到可行解与证明差距

任务有持续时间、资源需求和前置依赖，团队资源容量有限。系统必须拒绝未知依赖、自依赖和环，并输出满足依赖与容量约束的计划。V1 的关键路径优先列表调度能快速得到可行解，但启发式不保证最短工期。

V2 同时提供两条路径：

- 贪心调度处理常规规模，快速得到确定性可行解；
- 小规模精确搜索枚举并剪枝，得到最优工期，作为教学 oracle。

精确解的价值不仅是“再给一个答案”，更是量化贪心解与最优解之间的差距。没有 oracle 时，一个看起来合理的 makespan 很难说明质量如何。

### 5.2 DAG、拓扑序和关键路径

若 `B` 依赖 `A`，图中添加 `A -> B`。Kahn 算法按入度归零推进；零入度集合使用最小堆，确保多个合法拓扑序中优先选择较小编号，输出可复现。若处理顶点数少于任务数，剩余部分必有环。

关键剩余长度按反向拓扑 DP 计算：

```text
remaining(task) = duration(task) + max(remaining(dependent))
```

ready queue 优先考虑 `remaining` 较大的任务，减少阻塞长链的风险。它是启发式优先级，不是最优性证明；文档和代码注释都应明确这一边界。

### 5.3 为什么升级为“区间加 + 区间最大值”懒标记树

时间离散为左闭右开槽位 `[start, end)`。判断任务能否放入某窗口，只需查询窗口最大占用并检查：

```text
QueryMax(start, end) + resourceUnits <= capacity
```

任务落位后，整个区间占用增加 `resourceUnits`。V1 逐点更新需要 `O(duration · log H)`；V2 的懒标记线段树把区间增加推迟到真正访问子节点时，一次预留降为 `O(log H)`。

懒标记的关键不变量是：节点最大值和最小值都已包含尚未下推的统一增量；访问子节点前必须 `PushDown`，合并父节点时分别取子节点最大/最小。最大值证明正增量安全，最小值证明负增量不会下溢；内部用 `Int128` 保存延迟增量，因为两个合法 `long` 值之差可能需要 65 位。
更新会先预计算并记录触及节点快照，任何溢出都整体回滚；因此一次 `RangeAdd` 成功后，未来查询不会在下推时才发现潜伏溢出。区间统一采用 `[start, end)`，持续时间自然满足 `end - start = duration`，相邻任务不会重复占用边界槽位。

### 5.4 小规模精确解为什么必须设置上限

资源约束项目调度是组合爆炸问题。精确求解器先固定确定性拓扑顺序，再为每个任务枚举所有可能改进上界的整数起点，使用当前最好工期做上界，并用依赖链、剩余工作量等下界剪枝。即使如此，任务数和时间跨度增长后仍会指数膨胀。

因此公开 API 明确限制为最多 8 个任务、持续时间总和最多 32。内部另有 2,000,000 个搜索节点预算：
即使输入满足前两项，病态实例在预算内仍未穷尽时也会抛出 `InvalidOperationException`；启用追踪时，抛出前还会记录 `ExactSearchAborted`。
算法不会把当前最好计划冒充为已证明最优。只有正常返回的比较结果才携带最优性证明。测试通过 internal 构造参数把预算降为 1，在第二个节点稳定触发中止，从而不必真的消耗两百万节点也能持续验证该契约。
生产系统通常会采用 CP-SAT、整数规划或专业调度器。

成功完成的精确搜索还必须保持确定性分支顺序；否则不同运行虽都得到最优解，搜索轨迹和同工期方案可能变化，给教学追踪和回归测试带来噪声。

### 5.5 应验证哪些不变量

每个计划都必须满足：

1. 每个任务恰好出现一次；
2. `Start >= 0` 且 `End = Start + Duration`；
3. 开始时间不早于全部依赖的结束时间；
4. 任意时间槽的总资源不超过容量；
5. 拓扑序中每条依赖边起点都在终点之前；
6. 精确求解器返回的工期不大于同输入的贪心工期；
7. 在足够小的输入上，精确结果与独立穷举 oracle 一致。

只断言 makespan 不够：遗漏任务也可能产生很小的工期。先验证可行性不变量，再比较优化目标。

### 5.6 复杂度与限制

设任务数为 `V`、依赖数为 `E`、离散时间跨度为 `H`：

- 确定性 Kahn：`O((V + E) log V)`；
- 关键路径 DP：`O(V + E)`；
- ready queue：`O(V log V)`；
- 每次区间查询和预留：`O(log H)`，寻找起点仍可能扫描多个时间点；
- 精确求解：最坏指数级，只适用于明确上限内的小实例。

教学版没有可抢占任务、多技能人员、日历、切换成本和动态事件。它重点展示“快速启发式 + 小规模精确 oracle”如何形成可解释的工程组合。

## 6. 项目四：迷你存储引擎

### 6.1 应用场景与最小契约

迷你存储引擎模拟一个单进程、内存主导、可从日志恢复的键值库。它支持：

- `Put(key, value)` 插入或覆盖；
- `TryGet(key, out entry)` 点查；
- `Delete(key)` 逻辑删除；
- `RangeScan(fromInclusive, toExclusive)` 按键有序范围扫描；
- 重启后重放 WAL，恢复最后已提交状态。

这个项目把前面分散学习的树、概率结构、缓存和持久化协议放到同一条读写路径。重点不是复制成熟数据库，而是理解“索引、加速层、事实来源和恢复”为什么必须分工。

### 6.2 为什么主索引选择 B+ 树

B+ 树的内部节点只保存分隔键与子指针，实际记录集中在叶节点；叶节点按键有序并相互连接。因此：

- 点查沿树高下降，复杂度 `O(log n)`；
- B+ 树惰性范围扫描先定位起始叶，再按需沿叶链读取 `k` 个物理条目，约 `O(log n + k)`；消费者停止后枚举立即停止，不会按整棵树 `Count` 预分配或物化；
- 高扇出降低树高，也对应真实存储系统按页组织数据的思路。

分裂时要保持三个不变量：节点键有序；非根节点满足容量下界；父节点分隔键正确区分相邻子树。叶链还必须与树内中序顺序一致，否则点查可能正确而范围扫描漏项。测试应同时遍历树结构和叶链，不能只验证 `Get`。

教学版 B+ 树以内存对象模拟页，没有实现磁盘页编号、页缓存、合并回收和并发锁。它展示的是结构不变量，不是生产数据库页面管理器。

### 6.3 Bloom Filter 为什么只能回答“可能存在”

Bloom Filter 用多个哈希位置记录键。只要某一位为 0，键一定不存在；所有位都为 1，只能说明可能存在。读路径因此是：

1. Bloom 判断“一定不存在”时快速返回；
2. 判断“可能存在”时仍查询 B+ 树；
3. 绝不能把 Bloom 的阳性结果当作真实记录返回。

它允许假阳性，不允许假阴性。删除键时不能简单清零对应位，因为这些位可能被其他键共享；教学实现保持稳定过滤器语义，真实存在性始终由主索引决定。测试应断言所有已插入键从不被判为“不存在”，并把假阳性率作为统计观察，而不是要求永远为零。

### 6.4 LFU 缓存为什么不是事实来源

LFU 缓存优先淘汰访问频率低的记录，并用确定性规则处理相同频率。它只优化热点点查：缓存未命中必须回到 B+ 树；写入、覆盖和删除必须同步更新或失效缓存。

把缓存视为可丢弃派生状态很重要。崩溃恢复只重建主索引，不需要恢复 LFU 的历史频率；否则缓存会错误地参与持久化正确性。
教学实现的缓存值携带记录版本，并在写入时覆盖为最新命中、删除时覆盖为确定未命中；漏掉任一步都可能返回旧值，因此缓存一致性也是测试不变量。

### 6.5 为什么 WAL 必须先于内存修改

预写日志的顺序是：

```text
序列化操作 -> 追加 WAL -> 确认日志写入 -> 修改内存索引和缓存
```

如果先改内存再写日志，进程可能在两步之间崩溃：调用方看到写入成功的内存状态，却没有任何可恢复证据。WAL 先写让重启时可以顺序重放 `Put` 和 `Delete`，重建最终状态。

日志记录包含操作种类、键和值；`Put` 明确拒绝 `null`，`Delete` 使用独立操作与 tombstone，损坏的 Put-null 不会被悄悄解释成删除。序列号必须严格递增，重放同一已提交前缀得到相同最终状态。

每条 JSON 后的 LF 换行是最小提交标记。崩溃留下的最后一个无 LF 片段不会回放，并在重新追加前从最近提交边界截断；中间损坏或已经带 LF 的坏记录仍明确失败，不能静默跳过。
教学版不承诺事务原子性、校验和、中间记录修复、checkpoint、跨记录事务或多进程并发。“可恢复”只表示已刷新且带提交标记的记录可按顺序重放；它不是成熟数据库的 durability 协议。

### 6.6 一次读写如何经过四种结构

写入路径：配置 WAL 时先追加并刷盘，再更新 B+ 树，随后把 LFU 覆盖为最新命中，并把键加入 Bloom。
删除路径同样先追加 `Delete` 记录，再在 B+ 树中写入 tombstone，并把 LFU 覆盖为确定未命中；Bloom 不承担删除真实性。

点查路径：先看 LFU；未命中时用 Bloom 排除确定不存在的键，此时直接返回且不回填缓存；仍可能存在时查 B+ 树。
B+ 树命中时缓存值，遇到墓碑或 Bloom 假阳性时缓存确定未命中，避免热点不存在键反复访问树。
范围扫描直接使用 B+ 树叶链，因为 LFU 只覆盖热点个体，Bloom 也不支持顺序关系。

这个分工可以概括为：WAL 是恢复证据，B+ 树是有序事实索引，Bloom 是负查询加速器，LFU 是热点加速器。任何加速层都不能改变主索引语义。

### 6.7 复杂度、限制与运行

设记录数为 `n`、扫描返回数为 `k`、Bloom 哈希函数数为 `h`：

- B+ 树点查/写入：`O(log n)`；
- 存储范围扫描：`O(log n + p)`，`p` 是为得到最多 `k` 个活跃结果而经过的物理记录数；大量墓碑时 `p` 可显著大于 `k`；
- Bloom 查询/写入：`O(h)`；
- LFU 点查、写入和淘汰平均 `O(1)`；直接调用通用缓存的 `Remove` 时，极端情况下会扫描频率桶重算最小频率；
- 恢复：`O(numberOfLogRecords · indexUpdateCost)`。

```powershell
dotnet run --project DataStructureAndAlgorithm.Scenarios.MiniStorage -c Release
dotnet run --project DataStructureAndAlgorithm.Scenarios.MiniStorage -c Release -- --trace json
dotnet run --project DataStructureAndAlgorithm.Scenarios.MiniStorage -c Release -- --trace mermaid
```

建议先执行“写入 A、写入 B、覆盖 A、删除 B”，手算 WAL 和最终键空间，再创建新引擎重放日志。随后检查点查、范围扫描和缓存命中是否与恢复前一致。

## 7. 四个项目共同展示的 C# 最佳实践

### 7.1 用不可变记录表达快照结果

输入和输出优先使用 `record` / `record struct`，让值相等语义和解构更自然。内部索引仍可变，但只通过引擎方法维护不变量。返回集合采用只读视图或快照，防止调用方绕过 API 修改历史结果。

### 7.2 参数验证放在公共边界

公共方法使用 `ArgumentNullException.ThrowIfNull`、`ArgumentOutOfRangeException` 和带参数名的 `ArgumentException`。验证一次后，核心循环依赖已建立的前置条件，避免到处重复防御。精确调度的规模限制、扫描区间顺序和空键策略都属于公开契约。

### 7.3 现代语法服务于意图，而不是炫技

C# 14 集合表达式、模式匹配、目标类型 `new`、`record` 和 `required` 成员可以减少样板代码，但算法的边界和状态转移仍应显式。复杂循环宁可使用有含义的局部变量，也不要把 BM25、残量边更新或线段树下推压成难以断点调试的一行表达式。

### 7.4 注释解释“为什么”

高价值注释应解释：为什么区间是左闭右开、为什么 Bloom 阳性仍要查树、为什么反向残量边费用取负、为什么精确求解有规模上限。低价值注释只是把 `index++` 翻译成“索引加一”。教学代码的目标是让读者能从注释恢复推理，而不是让每行都有中文。

### 7.5 不依赖哈希枚举顺序

所有用户可见结果、追踪状态键和相同分数候选都要定义显式比较器。比较器逐字段调用 `CompareTo`，不使用整数相减，避免溢出。确定性不是算法正确性的全部，却是跨平台测试、差分比较和性能趋势可解释的前提。

### 7.6 缓存与概率结构不能拥有业务真相

路线 LRU、查询缓存、LFU 和 Bloom 都是可重建加速层。缓存键必须覆盖影响结果的版本状态，写入和删除必须维护失效规则；任何缓存未命中或 Bloom 阳性都不能改变领域结果。先实现无缓存正确路径，再加入加速层并做等价测试。

### 7.7 可选观察器不能反向破坏领域提交

四个场景把注入的 `IAlgorithmTraceSink` 包装为 `BestEffortAlgorithmTraceSink`。普通日志、UI 或测试接收器异常只增加丢弃计数，不会让“索引或 WAL 已提交”的操作向调用方报失败；否则调用方重试可能制造重复写入或搜索双状态。内存耗尽、栈溢出和访问冲突等进程级故障仍然传播，不能伪装成普通日志丢失。

回归测试使用必定抛异常的 sink，逐个运行配送、搜索、调度和带 WAL 的存储，并在存储重启后再次核对已提交值。这个测试证明的是隔离边界，不是说追踪丢失无需监控；显式创建装饰器的调用方仍可检查 `DroppedEventCount`。

## 8. 把正确性升级为“持续可证明”

这里的“证明”不是声称测试等价于形式化证明，而是建立一条持续运行、彼此独立的证据链。每次代码变化都重新检查契约、不变量、参考模型、可观察性和性能趋势，使错误更早、更容易定位。

### 8.1 第一层：把不变量写成可执行断言

每个结构都先列出不因输入变化而改变的规则：B+ 树键序与叶链一致、线段树父节点最大值正确、残量容量非负、匹配端点唯一、位置列表递增、WAL 重放顺序稳定。测试不应只断言最终 JSON，而应在最小操作后检查这些结构性规则。

不变量测试回答“结果是否自洽”，但不一定回答“是否为最优答案”。因此还需要独立 oracle。

### 8.2 第二层：模型、性质与差分测试

- 模型测试：用简单但明显正确的结构作参照，例如 `SortedDictionary` 对照 B+ 树、直接数组对照懒标记树。
- 性质测试：让 FsCheck 生成一族小输入，检查排序性、幂等性、恢复前后等价、容量不超限等普遍规则。
- 差分测试：让优化实现与不同思路的 oracle 处理同一输入，例如最小费用流对照小规模匹配穷举、BM25 候选对照直接扫描、精确调度对照更小规模的开始时间完整枚举。
- 状态机测试：生成 `Put/Get/Delete/Scan` 或缓存访问序列，每一步都与参考模型比较，而不是只比较最终状态。

安全阀也要可测试：精确调度的生产预算保持两百万节点，测试通过 internal 注入一个极小预算，确定性触发 `ExactSearchAborted` 与异常；这样验证的是语义，而不是 CI 机器能否快速跑完两百万节点。

为什么强调“小而可缩减”？随机大输入失败后很难理解。受控小输入既能覆盖大量组合，又允许 FsCheck 缩减为最小反例。oracle 必须比被测实现更简单且思路不同；复制同一算法只会让两个实现共享同一错误。

### 8.3 第三层：稳定的 trace schema

四个场景共用可选 `IAlgorithmTraceSink`。JSON 模式顶层保持 `{ result, trace }`，事件包含显式 schema version、步骤、算法、阶段、说明和只读状态。schema version 的意义是：当事件字段或语义未来变化时，消费者可以明确拒绝、迁移或兼容，而不是静默误读。

端到端 CLI 契约直接解析整段 stdout，字段名区分大小写且禁止静默扩展；事件 `step` 必须严格等于 `1..N`。场景内部再用 best-effort 装饰器隔离接收器异常，使“可观察”既稳定又不会改变领域提交。

追踪契约应验证：

1. 开启追踪前后领域结果完全相同；
2. 步骤从 1 连续递增；
3. 状态快照不会被后续修改回写；
4. 数值使用 `InvariantCulture`，状态键按 Ordinal 排序；
5. Mermaid 正确转义引号、反斜线和换行，并保持稳定末尾换行；
6. 非法命令行模式以约定退出码失败。

追踪只记录阶段和领域决策，不记录每次比较或树节点访问。否则观察本身会改变复杂度并淹没有价值的信息。trace 证明的是“观察契约没有漂移”，不能替代算法结果测试。

### 8.4 第四层：跨平台 CI

同一 Release 构建和测试应至少在 Windows 与 Linux 运行。跨平台矩阵能发现路径分隔符、换行、大小写、区域性数字格式和文件锁等本地单机难以暴露的问题。质量门禁还应包括格式、分析器、覆盖率和关键模块变异测试，但不要把覆盖率百分比误解为正确率。

CI 失败时先区分：编译/测试是真实代码错误，还是文档换行、coverage 路径和 shell glob 等平台差异。修复基础设施后仍必须保留相同语义门禁，不能通过跳过测试获得绿色状态。

当前 Release 质量快照（2026-08-15）为构建 `0 warning / 0 error`、`465/465` 测试通过、行覆盖率 `91.94%`、分支覆盖率 `84.80%`；最近一次 B+ 树、懒标记树、BK-tree、Bloom、LFU、最小费用流六文件的 Stryker Basic 验证（2026-07-18）分数为 `81.07%`（334 个有效变异）。快照会随代码与测试增长而变化；稳定契约是全部 Release 测试通过、行覆盖率至少 `80%`、分支覆盖率至少 `70%`，变异分数不低于 `60%` break 阈值。

### 8.5 第五层：观察基准趋势，不设脆弱时间阈值

当前 `ScenarioBenchmarks` 固定覆盖六条工作负载：CityDelivery 规划、MiniSearch V2 建索引并执行 BM25、调度贪心、固定小实例精确调度，以及 MiniStorage 同一热点/Bloom-negative 工作负载在 trace 关闭和开启时的两条基准。当前唯一直接 A/B 是存储 trace 开关；其他结果用于保存同输入的长期时间与分配趋势，不应被描述成尚不存在的实现对照。

后续最值得补充的参数化 A/B 基准包括：

- 位置索引判定与重新扫描正文；
- 懒标记区间更新与逐点更新；
- 启用/禁用 Bloom、LFU 的主索引访问；
- 不同任务数下精确调度的组合增长。

不要在共享 CI 中写“必须小于 2 ms”这类硬阈值。虚拟机负载、CPU 频率和运行时升级都会产生噪声。更可靠的方式是上传结构化结果、固定数据规模，按周观察中位数和分配量趋势；只有跨多次运行的显著回退才进入调查。

### 8.6 证据链如何配合

| 证据 | 擅长发现 | 不能单独证明 |
| --- | --- | --- |
| 示例/回归测试 | 已知边界和历史缺陷 | 未见过的输入族 |
| 不变量测试 | 结构是否自洽、约束是否违反 | 结果是否全局最优 |
| 模型/差分测试 | 优化实现与独立答案是否一致 | 超出 oracle 规模的全部输入 |
| 性质/状态机测试 | 操作序列与输入族问题 | 生产环境所有故障 |
| 变异测试 | 断言是否能杀死有意义的错误 | 没有建模的需求 |
| trace contract | 可观察性与输出协议是否稳定 | 算法本身正确性 |
| 基准趋势 | 时间和分配回退 | 语义正确性 |

持续可证明的关键不是选择一种“最强测试”，而是让不同证据尽量独立。每增加一个优化，都要保留简单正确路径或小规模 oracle，验证优化没有改变语义。

## 9. 推荐的八周学习路线

### 第一周：契约、不变量与追踪

运行四个项目的普通 JSON、追踪 JSON 和 Mermaid。为每个项目写出输入契约、领域目标、三个核心不变量和一个模型限制。确认开启追踪不改变领域结果。

### 第二周：配送 V2

手算 A* 候选、最大匹配和同流量最小费用方案。自己实现一个两车两单穷举 oracle，再解释残量反向边为什么允许纠正早期选择。

### 第三周：搜索 V2

手工建立位置倒排表，实现两个有序位置列表的短语/邻近合并。分别比较词频排序和 BM25，画出 BK-tree 查询时保留的距离区间。

### 第四周：调度 V2

先写 DAG 和资源可行性检查，再实现区间加/最大值懒标记。构造一个贪心非最优反例，用小规模精确解量化差距，并解释规模上限。

### 第五周：迷你存储引擎

依次学习 B+ 树叶链、Bloom 单向保证、LFU 失效和 WAL 顺序。对同一操作序列比较运行中状态、重启恢复状态和 `SortedDictionary` 参考模型。

### 第六周：性质与状态机

为四项目各设计至少一条性质。生成器保持输入小且合法，oracle 使用直接扫描、完整排序、简单数组或穷举，不复制被测优化算法。观察失败时如何缩减。

### 第七周：跨平台契约与性能趋势

阅读 CI 矩阵，理解 Windows/Linux 差异。运行短基准只验证基准可执行，再进行正式多轮采样；记录输入规模、运行时和分配量，不凭单次数字下结论。

### 第八周：隐藏实现重写

只保留公开 API、测试和本指导，独立重写一个项目的核心路径。完成后回答：目标函数是什么、不变量是什么、复杂度瓶颈在哪里、哪个优化由什么证据支持、生产化还缺什么。

## 10. 可继续扩展的方向

### 配送

- 在当前 Johnson 势能逐次最短增广路之外，比较 cost-scaling、容量缩放和整数费用表示的适用条件与工程代价。
- 加入时窗、车辆多单路线和容量累积，比较 VRP 与当前二分匹配模型。
- 设计地图增量版本与缓存精细失效。

### 搜索

- 支持文档删除、段合并和压缩 posting。
- 比较 BM25 参数与字段权重，加入标题/正文分域。
- 在现有 Rune 边界之上加入 Unicode normalization、语言相关 tokenizer 和同义词扩展。

### 调度

- 加入可抢占、多资源种类和任务切换成本。
- 比较分支限界、动态规划、整数规划和 CP-SAT。
- 为下界质量和搜索节点数建立基准趋势。

### 存储

- 增加页编号、页缓存、校验和和 checkpoint。
- 处理截断日志与部分写入，区分 logical recovery 和 durability。
- 研究 MVCC、快照隔离、LSM Tree 与 B+ Tree 的读写权衡。

## 11. 阶段验收清单

完成本阶段后，应能在不看实现的情况下解释并完成：

- 把“最大数量，其次最小成本”翻译为最大流量上的最小费用目标。
- 说明弱连通预筛为何不能替代有向最短路。
- 从位置倒排表推导短语和邻近查询，并解释 BM25 的三个权重来源。
- 说明 BK-tree 的剪枝依据及其最坏情况。
- 写出懒标记区间加的最大值、最小值与 `Int128` 延迟增量不变量，并使用左闭右开区间避免边界歧义。
- 区分调度可行解、启发式解和小规模精确最优解。
- 解释 B+ 树惰性叶链、Bloom 假阳性、LFU 饱和频率与 WAL 先写/换行提交顺序。
- 为每个综合项目设计不同于被测实现的简单 oracle。
- 说明示例、性质、差分、变异、trace contract 和基准趋势分别能证明什么。
- 在 Windows 与 Linux 上保持确定性输出和稳定追踪协议。
- 明确指出四个教学项目距离生产系统仍缺少的并发、持久化、规模和运维能力。

真正掌握的标志不是记住四条流水线，而是需求变化后仍能从目标函数、契约、不变量和复杂度重新推导设计，并能用持续运行的证据说明“为什么相信它仍然正确”。
